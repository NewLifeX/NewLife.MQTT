# MQTT 集群需求文档

> 版本：v2.0（面向亿级规模重构） | 日期：2026-07-14
> 对应主文档：[需求文档](需求文档.md) | 功能清单：[集群-功能清单](集群-功能清单.md) | 架构设计：[集群-架构设计](集群-架构设计.md)

## 1. 背景与愿景

### 1.1 背景

NewLife.MQTT 已在单机 Broker 场景验证了高性能（百万级吞吐）和协议完整性（MQTT 3.1/3.1.1/5.0）。然而单机节点存在上限：

- **容量瓶颈**：单机 TCP 连接数受操作系统和内存限制（当前 400 万+），无法无限扩展
- **单点故障**：节点宕机导致全部设备离线，无故障转移能力
- **跨节点互通**：不同节点上的订阅者无法彼此发现和通信
- **主题路由瓶颈**：当前 RPC 广播模式要求每个节点持有全量订阅关系，节点数 > 50 后网络和内存开销不可持续

当前 `ClusterServer` 已实现 RPC 集群基础通信（节点管理 / 订阅同步 / 消息转发 / 会话迁移）。面向 **百万至百亿级设备** 场景，需要在主题路由维度实现质的飞跃——从「全量复制」到「分片路由」。

### 1.2 愿景

NewLife.MQTT 集群的愿景分三个层次：

| 层次 | 规模 | 目标 |
|------|------|------|
| **基础集群** | 3~50 节点 / 百万级设备 | 单集群全连接，零配置自动组网，开发者即可运维 |
| **扩展集群** | 50~1000 节点 / 亿级设备 | 主题分片 + 多层路由，节点仅持有本地+分片订阅 |
| **超大集群** | 1000~10000+ 节点 / 百亿级设备 | 多层分级 + 区域自治 + 全局协调，接近无限水平扩展 |

**核心设计哲学**：线性扩展代价——集群规模扩大 N 倍时，单节点资源消耗增长不超过 O(log N)，而非当前的 O(N)。

### 1.3 核心目标

| 编号 | 目标 | 层级 | 一句话描述 |
|------|------|------|-----------|
| M1 | 节点管理 | 基础 | 节点发现、加入、心跳、离开、故障剔除 |
| M2 | 订阅同步 | 核心 | 跨节点订阅关系一致，客户端订阅任意节点即可全局可见 |
| M3 | 消息转发 | 核心 | 消息发布到任意节点，自动投递给所有匹配的远程订阅者 |
| M4 | 会话迁移 | 核心 | 客户端重连到不同节点时自动恢复会话，不丢失订阅和离线消息 |
| M5 | 一致性保证 | 架构 | 元数据（订阅关系）强一致，消息交付遵循 MQTT QoS 语义 |
| M6 | 持久化 | 扩展 | 会话和离线消息可选持久化到 Redis 或数据库，服务重启不丢失 |
| M7 | 可观测性 | 运维 | 集群健康状态、节点指标、事件日志可监控 |
| M8 | 集群安全 | 基础 | 共享密钥 ClusterSecret + 局域网自动信任 |
| M9 | 大规模主题路由 | 架构 | 主题分片 + 多层路由 + 布隆过滤器，支撑百万至百亿级设备 |

## 2. 功能需求

### 2.1 M1 节点管理

- **M1-1 节点加入**：节点启动时向集群注册，携带节点信息（地址、版本、能力），集群返回确认。
- **M1-2 心跳保活**：节点定时发送心跳（默认 15 秒），更新活跃时间戳。
- **M1-3 节点离开**：节点正常关闭时优雅退出集群，通知其他节点移除。
- **M1-4 故障剔除**：心跳超时（默认 5 分钟）自动将节点标记为不可用并清理其订阅关系。
- **M1-5 自动发现**：同一局域网内节点通过 UDP 广播自动发现并加入集群，无需手动配置。
- **M1-6 手动配置**：通过配置项 `ClusterNodes` 指定节点地址列表，适用于跨网段和生产环境。
- **M1-7 注册中心发现**：支持通过 Stardust 注册中心 / Consul 发现节点（SPI 扩展）。
- **M1-8 多层拓扑组织**：节点可声明角色（Edge / Regional / Core），组成分层的集群拓扑结构，上层节点仅持有聚合路由信息。
- **M1-9 连接聚合网关**：Edge 节点支持连接聚合模式，将大量设备连接汇聚为少量与上层节点的逻辑连接，减少上层连接压力。

### 2.2 M2 订阅同步

- **M2-1 订阅注册**：客户端订阅主题时，将订阅关系（TopicFilter + QoS + ClientId）同步到集群中相关节点（根据分片策略确定目标节点集，而非全量广播）。
- **M2-2 退订注销**：客户端退订时，从集群中相关节点移除对应订阅关系。
- **M2-3 订阅增量同步**：仅同步变化的订阅，不每次全量广播。
- **M2-4 订阅全量恢复**：节点重启或长时间落后时，从集群同步全量订阅快照。
- **M2-5 订阅清理**：节点离线或会话过期时，自动清理其所属订阅关系。
- **M2-6 布隆过滤器同步**：订阅信息不直接全量复制，改为同步紧凑的布隆过滤器（Bloom Filter），以极低空间代价支持快速"是否存在匹配订阅"判断。支持定期重建以控制误判率。
- **M2-7 订阅分片存储**：按主题哈希分片，每个分片由固定的节点子集持有订阅数据，单节点不存储全集群订阅，内存开销随集群规模 O(1/N) 线性缩减。

### 2.3 M3 消息转发

- **M3-1 主题匹配转发**：消息发布时，根据主题过滤器匹配远程节点上的订阅者，仅转发到有匹配订阅的节点。
- **M3-2 QoS 语义保持**：跨节点转发保持原始 QoS 等级（MQTT QoS 0/1/2）。
- **M3-3 环路防护**：消息转发过程中检测环路，避免无限循环（TTL 最大跳数 + 已访问节点列表）。
- **M3-4 本地优先**：消息优先投递给本地订阅者，再转发远程节点。
- **M3-5 遗嘱消息跨节点**：客户端异常断开时，遗嘱消息跨节点发布到所有匹配的订阅者。
- **M3-6 主题分片路由**：基于一致哈希（Consistent Hashing）将主题映射到分片，每个分片由固定节点子集负责。消息仅转发到目标分片所属节点，避免全量广播。新增/删除节点时仅影响相邻分片，最小化路由表扰动。
- **M3-7 多层分级路由**：Edge → Regional → Core 三级路由。Edge 节点将不匹配本地订阅的消息上报 Regional；Regional 在区域内转发；Core 处理跨区域转发。每层仅持有该层的聚合路由信息。
- **M3-8 布隆过滤器预检**：跨节点/跨区域转发前，先检查目标节点的布隆过滤器，快速跳过无匹配订阅的节点/区域，减少无效网络传输。
- **M3-9 热点主题自适应复制**：自动检测高频主题，将其订阅信息复制到更多节点（副本因子动态提升），分散热点流量；冷门主题仅在少数节点上持有，节约内存。
- **M3-10 批量合并转发**：对发往同一节点的多条小消息自动合并为批量传输，减少 RPC 调用次数，提升网络利用率。

### 2.4 M4 会话迁移

- **M4-1 持久会话识别**：客户端使用 CleanSession=0（MQTT 3.1.1）或 SessionExpiryInterval>0（MQTT 5.0）时启用持久会话。
- **M4-2 会话信息跨节点查询**：重连节点后，从原节点查询会话的订阅关系和离线消息。
- **M4-3 会话原子迁移**：获取远程会话后原子删除原节点会话，防止残留。
- **M4-4 离线消息迁移**：会话迁移时，未投递的 QoS 1/2 消息随会话一起迁移。
- **M4-5 会话超时清理**：持久会话过期后自动清理所有关联数据。

### 2.5 M5 一致性保证

- **M5-1 订阅强一致性**：订阅关系变更经过 Raft 共识协议确认，确保集群所有节点订阅视图一致。
- **M5-2 网络分区容忍**：分区恢复后自动从 Raft Log 回放修复不一致的订阅数据。
- **M5-3 Raft 快照**：节点重启后从 Leader 拉取全量订阅快照，快速恢复。
- **M5-4 2 节点降级**：仅 2 节点时降级为最终一致性模式（Raft 需要至少 3 节点形成多数派）。

### 2.6 M6 持久化

- **M6-1 Redis 持久化**：将持久会话、订阅关系、离线消息存储到 Redis（基于 `NewLife.Redis`）。
- **M6-2 数据库持久化**：将持久会话、订阅关系、离线消息存储到关系数据库（基于 `NewLife.XCode`，支持 SQLite/MySQL/SQL Server/Oracle）。
- **M6-3 混合模式**：运行时按配置选择持久化后端，支持切换。
- **M6-4 持久化 SPI**：`IStorageProvider` 接口定义持久化契约，位于 Storage 项目。核心库不持有持久化接口。

### 2.7 M7 可观测性

- **M7-1 集群指标**：节点数、活跃连接数、转发消息数、订阅总数发布到 `$SYS` 主题。
- **M7-2 健康检查**：`/cluster/health` API 返回各节点在线状态、延迟、版本。
- **M7-3 事件日志**：节点加入/离开/超时、订阅同步、转发异常记结构化日志。

### 2.8 M8 集群安全

- **M8-1 共享密钥 ClusterSecret**：集群端口（2883）通过 `ClusterSecret` 密钥校验节点接入。MQTT 客户端认证（1883）仍通过 `IMqttAuthenticator` 体系处理，ClusterSecret 不替代用户名/密码认证。
- **M8-2 局域网自动信任**：同一网段内节点（经 UDP 发现确认）自动免密钥接入，无需任何配置。
- **M8-3 跨网段强制密钥**：不同网段或手动配置的节点必须通过 ClusterSecret 校验。
- **M8-4 连接拒绝日志**：密钥校验失败记录日志并拒绝连接。

### 2.9 M9 大规模主题路由

#### M9-1 主题分片引擎
- **描述**：基于一致哈希（Consistent Hashing）将主题空间划分为固定数量的分片（Shard），每个分片由集群中一个节点子集（Replica Group）负责维护订阅关系。节点加入/离开时仅影响相邻分片的路由映射，最小化扰动。
- **虚拟节点**：每台物理节点映射为 100~500 个虚拟节点，均衡分布到哈希环上，避免物理节点配置差异导致的负载不均。
- **分片副本**：每个分片默认 3 副本（可配置），副本间通过 Raft 或 Gossip 保持订阅数据一致。读请求可从任意副本响应，写请求需多数派确认。

#### M9-2 多层分级路由
- **描述**：集群节点按角色分为 Edge / Regional / Core 三层，构建分级路由树。
- **Edge 节点**：直接承载设备连接，维护本地订阅 + 按需缓存热分片订阅。收到 PUBLISH 后：本地匹配 → 若命中则投递；未命中则上报 Regional。
- **Regional 节点**：聚合管辖范围内 Edge 节点的路由信息，维护本区域主题摘要。区域内跨 Edge 转发 + 向 Core 上报区域外主题。
- **Core 节点**：全局路由协调层，维护区域级布隆过滤器，跨区域转发。Core 层自身也可构成分片集群。
- **路由降级**：小规模部署（< 50 节点）可平坦模式运行，跳过层级直接全连接；中规模（50~1000）启用 Regional 层；超大规模（1000+）启用完整三层。

#### M9-3 布隆过滤器路由加速
- **描述**：每个节点/区域维护一个紧凑的布隆过滤器（Bloom Filter），编码本节点/区域的所有活跃主题过滤器。
- **预检流程**：跨节点转发前，先检查目标布隆过滤器是否有匹配可能 → 快速跳过无匹配目标 → 减少 60%~90% 无效 RPC 调用。
- **误判率控制**：默认 1% 误判率，根据订阅数自动调整过滤器大小。周期性（默认 60s）重建过滤器以清理已过期/已删除的订阅。
- **增量更新**：订阅变更时同步更新布隆过滤器（写时更新位），周期性全量重建确保收敛。

#### M9-4 热点主题自适应复制
- **描述**：动态检测高频主题的发布速率和订阅者数量，自动调整其分片副本因子。
- **冷主题**（< 100 msg/s）：默认 3 副本，单节点可服务。
- **温主题**（100~10000 msg/s）：副本因子提升至 5~9，副本分散到更多节点分担负载。
- **热主题**（> 10000 msg/s）：副本因子提升至 9~21，结合多级分发树将流量分散到大量叶子节点。
- **副本迁移**：副本因子变更时，基于一致哈希的增量迁移策略，仅移动变化的份额。

#### M9-5 批量合并传输
- **描述**：对发往同一目标节点的多条小消息（< 1KB）在发送端合并为单个 RPC 请求，减少网络往返和连接开销。
- **合并窗口**：可配置最大合并延迟（默认 5ms）和最大合并大小（默认 64KB），按时间或大小阈值触发发送。
- **流式适配**：大消息（> 64KB）不等待直接发送，避免增加延迟。

#### M9-6 主题订阅增量裁剪
- **描述**：订阅同步从当前的全量广播改为按分片定向推送，减少网络开销。
- **分片订阅变更**：仅将订阅变更分发给持有该分片的节点子集，而非全集群广播。
- **批量确认**：接收方批量确认订阅变更（默认每 100 条或每 100ms ACK 一次），减少确认消息数量。
- **全量快照**：当节点长时间落后或重启时，从分片 Leader 拉取该分片的全量订阅快照，快速追上集群状态。

## 3. 🧊 暂缓清单

| 功能 | 暂缓理由 | 解冻前提 |
|------|----------|----------|
| Raft 动态成员变更 | 静态配置满足当前需求 | 运行时动态增删节点需求明确时 |
| 多集群联邦（Cluster Federation） | 跨集群互通需求可通过桥接满足 | 百亿级以上跨区域场景 |
| 自适应弹性伸缩（Auto-scaling） | 需与容器编排平台深度集成 | K8s 部署方案成熟后 |

## 4. 不做什么

| 排除项 | 理由 |
|--------|------|
| 集群内部 TLS 加密 | 内网 RPC 端口不暴露公网；ClusterSecret 已提供接入层认证；TLS 增加证书管理复杂度，与「开发者即可运维」的理念冲突 |
| 第三方消息队列集成 | 已有规则引擎和 WebHook，可对接外部系统 |
| Kubernetes Operator | 属于 K8s 生态范畴，非核心功能 |
| 全局顺序消息 | 在分片架构下全局有序代价极高；MQTT 本身不要求全局有序，按主题有序即可 |
| 跨地域强一致集群 | 跨数据中心强一致延迟不可接受；推荐地域内强一致 + 地域间最终一致 |
