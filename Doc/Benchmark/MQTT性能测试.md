# MQTT 性能测试报告

NewLife.MQTT 是全功能 MQTT 服务端与客户端一体化组件，支持 TCP/WebSocket/QUIC/UDP 多协议接入和 MQTT V3.1.1/V5.0 双版本。本报告对服务端 **端到端消息吞吐**（发布→路由→订阅者接收）和 **消息编解码** 进行全面基准测试，**核心发现**：QoS0 单发布者峰值吞吐约 **53,800 msg/s**（5000条批次），QoS1 约 **20,200 msg/s**；编解码层纳秒级完成，不构成瓶颈；性能主要受限于 **主题匹配全表扫描** 和 **每消息堆分配**。

> **第二轮优化复测（2026-10-16）**：完成主题路由前缀索引、`IsMatch` Span 零分配重写、订阅快照与会话接收缓冲调优后复测（§9）：**QoS0 端到端峰值提升至 10.6 万 msg/s**（同日 A/B 为优化前的 1.8~2.9 倍），万级过滤器主题路由 120 ns/条恒定，每消息分配下降约 60~72%，初测定位的两大瓶颈均已消除。

## 2. 测试方法

### 2.1 端到端吞吐测试（MqttServerThroughputBenchmark）

在同进程内启动 MqttServer（随机端口），创建 1 个订阅者客户端（订阅 `bench/#`）和 N 个发布者客户端，并发发布指定数量消息，等待订阅者全部接收（最长 5 秒超时）。覆盖：

- **QoS 级别**：QoS0（Fire and Forget）、QoS1（At Least Once，需 PubAck）
- **消息批次**：1000 条、5000 条
- **并发发布者**：1、4、8（动态包含 CPU 核心数上限 8）

### 2.2 消息编解码测试（MqttMessageBenchmark）

单线程热路径测试，测量各类 MQTT 消息的序列化（ToPacket）和反序列化（ReadMessage）性能及内存分配。消息类型包含：Publish QoS0/QoS1（典型 IoT 载荷 ~35B）、Publish 1KB 大负载、Connect、Subscribe、Ping。

### 2.3 并发编解码测试（MqttConcurrentBenchmark）

多线程并发测试编解码吞吐量，每个线程执行 1000 次操作。线程数覆盖：1、4、8、20（CPU 核心数）、32。

## 4. 核心指标

### 4.1 端到端吞吐率（msg/s）

根据 Mean 值换算消息吞吐率（MessageCount / Mean）：

| 场景 | 1 发布者 | 4 发布者 | 8 发布者 | 
|------|--------:|--------:|--------:|
| **QoS0 × 1000 msg** | 32,258 | 16,166 | 8,096 |
| **QoS0 × 5000 msg** | **53,828** | 40,674 | 40,177 |
| **QoS1 × 1000 msg** | 21,400 | 16,133 | 9,095 |
| **QoS1 × 5000 msg** | **20,167** | 19,853 | 18,561 |

- **QoS0 峰值吞吐**：53,828 msg/s（单发布者，5000 条批次）
- **QoS1 峰值吞吐**：21,400 msg/s（单发布者，1000 条批次）
- **QoS0 vs QoS1**：QoS0 约为 QoS1 的 **2.5 倍**（因 QoS1 需要等待 PubAck 确认）

## 5. 对比分析

### 5.1 QoS0 vs QoS1（纵向对比）

| 5000 msg 场景 | QoS0 | QoS1 | QoS1 / QoS0 |
|--------------|-----:|-----:|-------------:|
| 1 发布者 | 92.89 ms | 247.94 ms | 2.67x 慢 |
| 4 发布者 | 122.93 ms | 251.85 ms | 2.05x 慢 |
| 8 发布者 | 124.45 ms | 269.43 ms | 2.17x 慢 |
| 分配/条 | 1.55 KB | 2.78 KB | 1.79x 多 |

**分析**：QoS1 需要服务端和客户端额外的 PubAck 消息交互，每条消息增加一次 RTT，导致吞吐降低至 QoS0 的 40%。内存多出约 80%，主要来自 PubAck 消息对象和 Inflight 管理。

### 5.2 多发布者扩展性（纵向对比）

| QoS0 × 5000 msg | Mean | msg/s | vs 1 发布者 |
|-----------------|-----:|------:|----------:|
| 1 发布者 | 92.89 ms | 53,828 | 基准 |
| 4 发布者 | 122.93 ms | 40,674 | -24.4% |
| 8 发布者 | 124.45 ms | 40,177 | -25.4% |

**分析**：4 和 8 发布者的吞吐几乎相同（~40K msg/s），说明瓶颈不在发布端而在 **订阅者接收端**（单个订阅者 TCP 连接的吞吐上限）。4→8 发布者无额外下降进一步证实了这一点。

### 5.3 小批次 vs 大批次（横向对比）

| QoS0 × 1 发布者 | 1000 msg | 5000 msg | 大批次优势 |
|-----------------|--------:|--------:|----------:|
| Mean | 31.00 ms | 92.89 ms | — |
| msg/s | 32,258 | 53,828 | **+66.8%** |
| 分配/条 | 1.54 KB | 1.55 KB | 持平 |

**分析**：大批次吞吐率显著更高（+66.8%），因为连接建立、主题匹配等固定开销被更多消息摊薄。每消息分配量持平说明无累积泄漏。

### 5.4 序列化 vs 反序列化（编解码对比）

| Publish QoS0 | 反序列化 | 序列化 | 倍数 |
|-------------|--------:|------:|-----:|
| 延迟 | 67 ns | 124 ns | 1.84x |
| 分配 | 224 B | 48 B | 0.21x |

**分析**：序列化耗时约反序列化 2 倍，但分配仅 48 B（一个 Packet 对象），远低于反序列化的 224 B（需构建完整消息对象）。在端到端链路中，编解码总耗时仅 ~191 ns/消息，远低于网络 IO 和路由开销（微秒级），**编解码不是瓶颈**。

## 6. 性能瓶颈定位

### 6.1 瓶颈概览

通过测试数据和源码分析，定位以下瓶颈（按影响排序）：

| 优先级 | 瓶颈 | 影响模块 | 严重性 |
|--------|------|---------|--------|
| P0 | 主题匹配全表扫描 | MqttExchange.Publish | 🔴 高 |
| P0 | IsMatch 每次 Split 字符串 | MqttTopicFilter.IsMatch | 🔴 高 |
| P1 | 订阅者列表 ToArray 拷贝 | MqttExchange.Publish | 🟠 中 |
| P1 | 每订阅者 new PublishMessage | MqttExchange.Publish | 🟠 中 |
| P2 | 单订阅者接收瓶颈 | MqttClient/TCP | 🟡 低 |
| P2 | QoS1 PubAck 同步等待 | MqttClient.PublishAsync | 🟡 低 |

> **更新（2026-10-16）**：P0 两项与 P1 的 ToArray 已在第二轮优化中修复；同时发现 P0 之上的更底层热点——每消息 8KB 接收缓冲分配，已通过会话接收缓冲调优化解。复测数据见 §9。

### 6.2 P0：主题匹配全表扫描（CPU 热点）

**位置**：`MqttExchange.cs` Publish 方法

```csharp
foreach (var item in _topics)  // 遍历所有注册的 topic filter
{
    if (!MqttTopicFilter.IsMatch(message.Topic, item.Key)) continue;
    // ...
}
```

**问题**：每条 PUBLISH 消息都需要遍历 `_topics` 字典中的 **所有** topic filter，复杂度 O(T)（T = topic filter 数量）。当系统有 10K 个 topic filter 时，每秒 50K 消息将产生 **5 亿次** IsMatch 调用。

### 6.3 P0：IsMatch 字符串分割开销（CPU + 内存）

**位置**：`MqttTopicFilter.cs` IsMatch 方法

```csharp
var topicFilterParts = actualTopicFilter.Split('/');  // 每次调用都分配新数组
var topicNameParts = topicName.Split('/');              // 每次调用都分配新数组
```

**问题**：
- **每次调用分配 2 个字符串数组**，典型 4 层主题（`a/b/c/d`）产生 2 × 5 = 10 个字符串对象
- 同一个 topic filter 被匹配 N 次（N = 消息数），但 Split 结果从不缓存
- 按当前吞吐 50K msg/s、单 topic filter 场景：**每秒 100K 次 Split 调用，约 50 万个临时对象**

### 6.4 P1：订阅者列表 ToArray

**位置**：`MqttExchange.cs` Publish 方法

```csharp
foreach (var sub in subs.ToArray())  // 每次 Publish 都复制整个订阅者列表
```

**问题**：即使只有 1 个订阅者，每条消息也会分配一个新数组。100 个订阅者时每条消息分配 100 × 8 = 800 B 的快照数组。

### 6.5 P1：每订阅者创建新 PublishMessage

**位置**：`MqttExchange.cs` Publish 方法

```csharp
var msg = new PublishMessage
{
    Topic = message.Topic,
    Payload = message.Payload,
    QoS = sub.QoS,
    Retain = sub.RetainAsPublished && message.Retain,
};
```

**问题**：当一条消息被路由给 N 个订阅者时，创建 N 个 PublishMessage 对象。对于广播场景（如 IoT 设备状态变更推送给所有监控端），1 条消息 × 1000 订阅者 = 1000 个 PublishMessage 对象。

### 6.6 P2：单订阅者接收瓶颈

测试数据显示 4 发布者和 8 发布者的 QoS0 吞吐率几乎相同（~40K msg/s），说明瓶颈已从发布端转移到单个订阅者 TCP 连接的接收能力。在生产环境中这通常不是问题（多个订阅者分散负载），但在扇入（fan-in）场景需注意。

## 7. 优化建议

### 7.1 P0 优先级（预期提升 30-50%）

#### A. 预编译 Topic Filter 缓存

在 Subscribe 时缓存 topic filter 的 Split 结果，避免 IsMatch 每次重复分割：

```csharp
// 在 SubscriptionItem 或独立缓存中存储预分割结果
class CachedFilter
{
    public String[] Parts;       // 预编译的分割结果
    public Boolean HasWildcard;  // 是否包含 +/#
}
```

**预期收益**：消除 IsMatch 中 50% 的 Split 开销和临时对象分配，每消息减少约 200-400B GC 压力。

#### B. 主题前缀索引

用 Dictionary 按主题第一层级建立索引，Publish 时只遍历匹配首级的 filter 子集，而非全表扫描：

```csharp
// Publish 时按首段快速定位
var firstPart = topic.AsSpan().Slice(0, topic.IndexOf('/'));
// 只遍历首段匹配 + 通配符(+/#) 的 filter
```

**预期收益**：当 topic filter 按前缀分散时，遍历量从 O(T) 降至 O(T/K)（K = 首级数量），大规模场景可减少 70%+ 匹配次数。

### 7.2 P1 优先级（预期提升 15-25%）

#### C. 订阅者列表使用 CopyOnWrite 快照

将 `List<SubscriptionItem>` 替换为 CopyOnWrite 模式，Subscribe/Unsubscribe 时生成新数组快照，Publish 时直接遍历快照无需 ToArray：

```csharp
// 订阅变更时（低频）创建新快照
volatile SubscriptionItem[] _snapshot;

// Publish 时（高频）直接读取快照，零分配
foreach (var sub in _snapshot) { ... }
```

**预期收益**：消除每条消息的 ToArray 分配，读写比典型为 1000:1 时效果显著。

#### D. PublishMessage 对象复用

对于同 QoS、同 Retain 的订阅者，复用同一个 PublishMessage 实例：

```csharp
// 按 (QoS, Retain) 分组，同组共享一个消息对象
PublishMessage? sharedMsg = null;
foreach (var sub in subs)
{
    if (sharedMsg == null || sharedMsg.QoS != sub.QoS || ...)
        sharedMsg = new PublishMessage { Topic, Payload, QoS = sub.QoS };
    session.PublishAsync(sharedMsg);
}
```

**预期收益**：广播场景下 N 个订阅者从 N 次 new 降至 1-3 次，减少 90%+ 消息对象分配。

| 编解码延迟 | **67-177 ns** | 卓越，纳秒级不构成瓶颈 |

| 每消息分配 QoS0 | **1.54 KB** | 中等，有优化空间 |
| 每消息分配 QoS1 | **2.77 KB** | 中等，PubAck 开销显著 |
| 主要瓶颈 | 主题匹配全表扫描 + Split | 可通过索引和缓存大幅改善 |
| 次要瓶颈 | ToArray + new PublishMessage | 可通过 CopyOnWrite 和对象复用改善 |

> 上表为初测（2026-03）基线结论；第二轮优化（2026-10-16）后的复测指标见 §9。

## 9. 第二轮优化与复测（2026-10-16）

> 本节为第二轮性能优化（主题路由前缀索引、`IsMatch` Span 零分配重写、订阅快照、会话接收缓冲调优）的复测数据。§3~§8 保留初测基线；端到端口径请以本节的「优化前/优化后」同日 A/B 为准。

### 9.1 优化项

| 优化项 | 内容 | 主要收益 |
|--------|------|---------|
| P0-A 主题路由 | `MqttExchange` 以首层主题段前缀索引（`_topicIndex` + `_wildcardFilters`）定位候选过滤器，替代全表扫描 | 万级过滤器下路由开销保持恒定 |
| P0-B 主题匹配 | `MqttTopicFilter.IsMatch` 改为 Span 逐段匹配；无通配符过滤器走字符串恒等快速通道；`$share/` 等前缀判断改 Ordinal | 匹配分配归零，字面量匹配 637→8.8 ns |
| P1 订阅快照 | 订阅列表写时复制快照，Publish 读路径无锁零分配；共享订阅轮询零分配选取 | 消除每消息 ToArray/HashSet 分配 |
| P2 接收缓冲 | `MqttServer.SessionBufferSize` / `MqttClient.ReceiveBufferSize` 默认 2048（原 8KB） | 每消息接收侧大对象分配下降约 60~70% |

### 9.2 主题匹配微基准（旧实现对照）

每项操作循环 10000 次，BenchmarkDotNet v0.15.8（`MqttTopicFilterBenchmark`）：

| 场景 | 旧实现（Split） | 新实现（Span） | 提速 | 旧分配 | 新分配 |
|------|---------------:|---------------:|-----:|-------:|-------:|
| 字面量精确匹配 | 637.6 ns | **8.8 ns** | **72×** | 352 B | **0 B** |
| 单层通配符 `+` | 561.7 ns | 62.9 ns | 8.9× | 328 B | **0 B** |
| 多层通配符 `#` | 1,375.7 ns | 47.3 ns | 29× | 280 B | **0 B** |
| 深层主题不匹配（7 层） | 679.9 ns | 10.5 ns | 65× | 496 B | **0 B** |
| 共享订阅匹配 | 835.8 ns | 77.3 ns | 10.8× | 392 B | 64 B¹ |

> ¹ 共享订阅需提取 `$share/{group}/` 前缀子串，为唯一保留的小额分配。

### 9.3 路由开销随过滤器规模的变化（旧实现对照）

单会话订阅 N 个不同前缀过滤器，发布命中其中一个（`MqttExchangeRoutingBenchmark`，含匹配与单次投递对象创建）：

| 过滤器数量 | 旧实现（全表扫描） | 新实现（前缀索引） | 提速 | 旧分配 | 新分配 |
|-----------:|------------------:|------------------:|-----:|-------:|-------:|
| 1 | 1,381 ns | **122 ns** | 11.3× | 376 B | 104 B |
| 100 | 134.5 μs | **116.6 ns** | 1,153× | 31.3 KB | 104 B |
| 10,000 | 13.95 ms | **120.5 ns** | 115,776× | 3.27 MB | 112 B |

- 新实现路由开销与过滤器数量无关（120 ns 量级恒定），旧实现在万级过滤器下每消息需 13.9 ms。
- 首层段分散时定位候选过滤器；同一首层段下的过滤器数量决定残留匹配量，通配符开头的过滤器走独立通配符桶（不与 `$` 主题匹配）。

### 9.4 端到端吞吐与分配（同日 A/B）

同一代码库、同一机器、同口径（事件驱动等待交付完成，消除轮询等待误差）优化前/后对照：

| 场景 | 优化前 Mean | 优化后 Mean | 耗时变化 | 优化后吞吐 | 分配（前 → 后） |
|------|-----------:|-----------:|---------:|----------:|---------------:|
| QoS0 × 1000 × 1 发布者 | 16.60 ms | **9.41 ms** | **-43%** | **106,292 msg/s** | 18.07 MB → 5.09 MB（-72%） |
| QoS0 × 1000 × 4 | 20.67 ms | **9.79 ms** | **-53%** | 102,145 msg/s | 15.50 MB → 5.06 MB |
| QoS0 × 1000 × 8 | 24.64 ms | 14.72 ms | -40% | 67,950 msg/s | 13.93 MB → 5.52 MB |
| QoS0 × 5000 × 1 | 135.85 ms | **47.57 ms** | **-65%** | **105,109 msg/s** | 85.23 MB → 25.44 MB（-70%） |
| QoS0 × 5000 × 4 | 112.92 ms | 91.55 ms | -19% | 54,615 msg/s | 65.66 MB → 28.09 MB |
| QoS0 × 5000 × 8 | 108.41 ms | 95.46 ms | -12% | 52,378 msg/s | 62.29 MB → 27.07 MB |
| QoS1 × 1000 × 1 | 74.89 ms | 65.82 ms | -12% | 15,193 msg/s | 20.06 MB → 7.96 MB |
| QoS1 × 1000 × 4 | 25.77 ms | 21.21 ms | -18% | 47,148 msg/s | 19.88 MB → 7.86 MB |
| QoS1 × 1000 × 8 | 25.51 ms | **14.10 ms** | **-45%** | 70,922 msg/s | 19.59 MB → 7.70 MB |
| QoS1 × 5000 × 1 | 374.97 ms | 332.09 ms | -11% | 15,056 msg/s | 100.34 MB → 39.82 MB |
| QoS1 × 5000 × 4 | 117.19 ms | 110.97 ms | -5% | 45,057 msg/s | 99.63 MB → 39.65 MB |
| QoS1 × 5000 × 8 | 85.40 ms | 70.56 ms | -17% | 70,863 msg/s | 97.12 MB → 38.48 MB |

- **QoS0 单发布者峰值吞吐 10.6 万 msg/s**（1000 条批）/ 10.5 万 msg/s（5000 条批），较同日优化前提升 1.8~2.9 倍，较初测（2026-03，53,828 msg/s）约 2 倍。
- **QoS1**：单发布者受逐条等待 PubAck 的 RTT 约束（~1.5 万 msg/s）；多发布者并发流水线下 4.5~7.1 万 msg/s。
- **每消息分配**：优化后 QoS0 约 5.1 KB/msg、QoS1 约 8 KB/msg，较优化前下降约 60~72%；Gen2 回收从频繁出现降至基本消失（QoS1 全程无 Gen2）。
- QoS0 多发布者大批次（5000×4/8）提升较小，瓶颈已转移至单订阅者连接接收与线程调度，而非路由或分配。

### 9.5 结论与后续

- **路由瓶颈消除**：主题路由由「每消息全表扫描 + 字符串分割匹配」变为「首层段索引 + Span 零分配匹配」，万级过滤器下 13.95 ms → 120 ns/条；微基准中字面量匹配提速 72 倍且分配归零；附带发现并修复热路径文化敏感 `StartsWith`（每次约 0.4 μs，占当时单次匹配成本的大头）。
- **接收缓冲**：v12 消息泵在启用入站管道后每个接收轮次更换接收缓冲（详见下），缓冲大小即每条消息的接收侧分配量级；会话级缓冲降至 2048 后，每消息分配下降约 60~70%。
- **端到端**：QoS0 峰值 10.6 万 msg/s（较优化前同日基线提升至 2~2.9 倍），全场景分配下降 60% 以上，GC 压力显著缓解。
- **遗留与建议**：
  - v12 接收环每次读取都会更换缓冲（管道共享切片导致接收槽快路径失效），数组池在高频租借下命中率低，是当前每消息剩余分配的主要来源；进一步的接收缓冲复用/池化建议在 NewLife.Core 侧评估。
  - QoS1 单发布者逐条等待 PubAck（RTT 串行）仍是该场景吞吐上限；`MQTT_5.0` 的 Inflight 窗口可缓解，属后续优化项。

## 10. 规模化实测与竞品口径对标（2026-10-16）

> §9 的 10.6 万 msg/s 是「单连接端到端」口径。本节用独立压测工具 [`Benchmark/LoadBench`](../../Benchmark/LoadBench/Program.cs)（双进程：Broker 进程 + 负载进程，可换机）测出「对标竞品口径」的规模化数据，并联网核实拆解竞品百万级数字的口径来源。

### 10.1 测试方法

QoS0、64B payload、每连接高频发布循环（连接独享消息对象，降低负载端自身开销）；Broker 与负载生成器分进程运行，Broker 端以 `MessagesReceived/MessagesSent` 为计数口径：

| 场景 | 命令 | 口径 |
|------|------|------|
| Broker 压测服务端 | `LoadBench server <port> <seconds>` | 每 2 秒打印收/发速率 |
| 多连接灌入 | `LoadBench pub <port> <conns> <seconds>` | N 发布连接并发，服务端收包 |
| N 对端到端（1:1） | `LoadBench pair <port> <pairs> <seconds>` | N 发布 × N 订阅，订阅端收包 |
| fan-out | `LoadBench mix <port> <pubConns> <subConns> <seconds>` | 订阅端全部订阅 `bench/#`，按投递数计 |
| 原始 TCP 对照 | `LoadBench rawserver/rawclient ...` | 无 MQTT 编解码的框架收发上限 |

### 10.2 实测结果（i9-10900K / .NET 10；Broker 与负载同机共享 10 核 20 线程）

| 口径 | 连接数 | 实测 | 说明 |
|------|-------:|-----:|------|
| 单连接端到端（§9） | 2 | **10.6 万 msg/s** | 1 发布 + 1 订阅 |
| N 对端到端（1:1 拓扑） | 64 | **~58~60 万 msg/s** | 32 对，服务端收发比 1:1 |
| Broker 收包（无投递） | 8 | ~80 万 msg/s | |
| Broker 收包（无投递） | 32~64 | **~125 万 msg/s（平台期）** | 加连接不再上升 |
| fan-out 投递 | 32 发布 × 16 订阅 | ~50 万投递/s | 1 发 16 收，按投递数计 |
| 原始 TCP 收包（对照） | 16 | ~190 万包/s（117 MB/s） | 无 MQTT 层的框架上限 |

**发现**：

- 单连接 10.6 万是「最窄几何」的结果：一条 TCP 连接的发送循环与接收排水串行，且负载与 Broker 共享 CPU。
- 多连接下 Broker 收包达 **~125 万 msg/s**，为原始 TCP 上限（190 万包/s）的约 66%，其余为 MQTT 解码/路由/消息泵成本；继续加连接不再上升——**单机（负载与 Broker 同机）是当前天花板**，官方基准均使用独立负载机。
- fan-out 场景投递 ~50 万/s（16 个订阅连接各 ~3 万/s），受同机 48 个客户端连接的 CPU 竞争限制。

### 10.3 竞品百万级数字的口径拆解

> 以下来源均已联网核实（2026-10-16），详见各官方页面。

| 声称数字 | 实际口径拆解 | 来源 |
|---------|-------------|------|
| EMQX 单节点 200 万 msg/s | 入站仅 **2,000/s**（20 发布 × 100 msg/s）；1000 订阅者 **fan-out ×1000**，按 Broker 出站计数 2,000,000/s；64 vCPU 单节点；QoS0/16B | emqx.com 单节点 200 万基准博客 |
| EMQX 集群 100 万+/s | **23 节点 × 64 vCPU**（≈1472 vCPU）；1:1 拓扑；按处理数计（未分入/出）；多数 pub/sub 对在同一节点 | emqx.com 1 亿连接博客 |
| HiveMQ 100 万 PUBLISH/s | **40 节点集群**；入 50 万 + 出 50 万（**双向合并计数**）；2 亿连接；QoS1 发布/QoS2 订阅；16B；**落盘**；**不含 PUBACK**（含则 2M/s） | hivemq.com 2 亿连接报告 |
| HiveMQ 每核 3,900 msg/s/core | 4 节点 ×32 vCPU；**入+出合计**；QoS1 **落盘**；1:1 拓扑、16B——官方最保守的每核数字 | hivemq.com per-core 博客 |
| NanoMQ 单核 20~25 万 | **500 订阅者 fan-out ×500**（入站仅 400/s）；1 核 1 线程；订阅端计数 | NanoMQ 官方 test-report |
| Mosquitto 20 万/s（单核） | **未找到官方基准出处**；最接近的第三方实测（2.0.15、关持久化、16 vCPU）：37.3k pub/s + 37.3k sub/s（≈7.5 万总流量/核） | VerneMQ 2015 博文转述；EMQX mqttbs |

| MQTTnet ~10 万/s | **未找到可核实来源**；官方仓库服务端吞吐基准方法被整段注释（名存实亡）；第三方客户端基准（经 Mosquitto、64B、同机回环、端到端）：QoS0 **3.77 万/s**、QoS1 1.23 万/s | MQTTnet 仓库；marcschier/mqtt-client 基准 |

**口径放大因子汇总**（相乘可解释 10²~10⁴ 倍差距）：

| 因子 | 典型倍数 | 依据 |
|------|---------|------|
| fan-out 按投递计数（1 发 N 收） | ×100 ~ ×1000 | EMQX 2M=×1000；NanoMQ=×500 |
| 集群节点数 | ×3 ~ ×40 | EMQX 23 节点；HiveMQ 3/10/40 节点 |
| 入+出双向合并计数 | ×2 | HiveMQ 明示 500k in + 500k out = 1M |
| QoS1 PUBACK 是否计入 | ×2 | HiveMQ 原文：含 PUBACK 则 2M/s |
| 独立负载机 vs 同机回环 | 结构性差异 | 所有官方数字均用独立负载机（Swarm/emqtt-bench/XMeter），HiveMQ 明确要求负载机与被测集群同规模 |
| QoS 级别 / 落盘 / payload / TLS | 2 ~ 10 倍视场景 | QoS0→QoS1 客户端侧约 2~3 倍；落盘与 TLS 视配置 |

### 10.4 结论

1. **10.6 万 msg/s 不是 Broker 容量，而是「单连接端到端」几何下的结果**；没有任何竞品公布过可比口径（per-connection 或单进程回环数字均未找到），与"百万级"营销数字不可直接比较。
2. **对标口径（Broker 端收包、多连接）下实测约 125 万 msg/s**，与竞品官方数字同一量级；N 对端到端（1:1、64 连接）约 58~60 万 msg/s。
3. 竞品百万/千万级数字的放大主要来自 **fan-out 计数（×100~1000）、集群规模（×3~40）、双向计数（×2）** 等口径因子；按已知最保守的官方每核口径（HiveMQ 3,900 msg/s/core，QoS1+落盘+入出合计）对照，本机 125 万收包/10 物理核虽有口径差异（QoS0、不落盘、单向、且负载同机竞争 CPU），量级对比并不落后。
4. 当前限制来自**单机**：负载生成器与被测 Broker 共享 10 核 20 线程，原始 TCP 上限也仅 ~190 万包/s；要定位 Broker 真实上限，需按厂商做法将负载机独立到另一台机器。
5. 与 .NET 生态同口径参照：单连接端到端 10.6 万 msg/s 约为公开第三方 .NET QoS0 基准（3.77 万/s，64B，经 Mosquitto 同机回环）的 2.8 倍。

NewLife.MQTT 编解码层性能卓越，端到端吞吐在中小规模（百级 topic、千级连接）下表现良好。主要受限于消息路由层的全表扫描和字符串分配，在万级 topic filter 场景下会成为显著瓶颈。建议优先实施 P0 优化（预编译缓存 + 前缀索引），可使大规模场景吞吐提升 30-50%。
